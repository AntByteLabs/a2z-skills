The test and production webhook URLs have different registration rules. A 404
can reflect either, but it can also have other causes. This guide preserves two
responses recorded on n8n 2.10.2; it is not a diagnosis of every webhook error. More automation guides are in
[Automation](/topics/automation/), the instance this was tested on is the one
from [self-host n8n on Coolify](/self-host-n8n-coolify/), and the wider failure
this belongs to is in
[why automations fail silently](/automations-failing-silently/).

## Two recorded registration failures returned 404

Every n8n webhook node gives you two URLs. A test URL under `/webhook-test/`
and a production URL under `/webhook/`. When neither is listening, both return
`404` in the probes below. Their message and hint fields distinguish the recorded cases.

<Callout type="note" title="Version clarification, 27 October 2026">
  The quoted errors below are preserved from the original test. Current n8n documentation
  uses publication terminology and describes a 120-second test listener. The old error’s
  toggle and one-call wording should not be read as a universal description of later
  versions.
</Callout>

Calling a production path with no active workflow:

```json
{
  "code": 404,
  "message": "The requested webhook \"POST does-not-exist-probe\" is not registered.",
  "hint": "The workflow must be active for a production URL to run successfully. You can activate the workflow using the toggle in the top-right of the editor. Note that unlike test URL calls, production URL calls aren't shown on the canvas (only in the executions list)"
}
```

Calling a test path with nothing listening:

```json
{
  "code": 404,
  "message": "The requested webhook \"does-not-exist-probe\" is not registered.",
  "hint": "Click the 'Execute workflow' button on the canvas, then try again. (In test mode, the webhook only works for one call after you click this button)"
}
```

Two things are worth noticing. The hint names the cause in both cases, which is
more than most 404s give you. And the production message quotes the HTTP method
before the path, `"POST does-not-exist-probe"`, where the test message quotes
the path alone. If you are logging these, that difference tells you which half
of the system answered without parsing the hint at all.

## Test listening is temporary

The error from this test describes one call after **Execute workflow**. It is
kept above as observed evidence, not rewritten to match newer documentation.
The current [Webhook workflow-development reference](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/workflow-development/)
describes a test listener that remains active for 120 seconds. Test mode is
therefore not a persistent endpoint for an external integration.

## Production registration is separate from saving

The current [Webhook node reference](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)
links production registration to workflow publication. Saving a draft and
publishing a workflow are distinct actions. Production data is examined through
the workflow's executions, rather than appearing on the editor canvas.

These documented rules explain why an editor test and an external production
request need to be interpreted separately. They do not establish that every
404 means an unpublished workflow; a wrong HTTP method or path also needs
consideration.

## When the host in the URL is wrong

On a self-hosted instance there is a third cause. generated webhook URLs depend on n8n’s
configuration and reverse-proxy setup. The [official reverse-proxy guidance](https://docs.n8n.io/hosting/configuration/configuration-examples/webhook-url/)
describes `WEBHOOK_URL` and proxy settings. The recorded Coolify setup also
changed `N8N_HOST` and `N8N_EDITOR_BASE_URL`; those variables do not all serve
the same purpose. A wrong generated host can direct a request elsewhere.

That is a different failure from the two above, and it looks different: you get
your proxy's error, or a connection failure, rather than n8n's JSON 404. The recorded JSON
responses identify n8n’s registration error. A different body alone cannot prove
that n8n was never reached: workflow responses and intermediary error pages can
have other formats. The host, headers and execution evidence matter too.

<WhatBroke>
  Both probes were run against a live instance, and the thing that surprised us
  was that the two cases are indistinguishable by status code. We expected the
  production URL to answer differently from the test URL, perhaps 404 against
  409 or 503. Both are 404. A monitor that alerts on status alone cannot tell an
  inactive workflow from a test URL that has already fired, and will report both
  as the same outage.

In these probes, `GET` returned 404 on the production path as well. A webhook
configured for POST should not be assumed to support GET; the method is part
of the endpoint’s configuration.

</WhatBroke>

## When the endpoint receives requests

Repeated executions need a different explanation from an endpoint that returns 404. Read [webhook retries and duplicate events](/webhook-retries-duplicate-events/) for delivery identity and retry behaviour. For an expression that cannot identify the matching earlier record, see [n8n item linking](/n8n-item-linking-explained/).
