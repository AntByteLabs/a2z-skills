You type a product code and get a date. You paste a clean export and a column of
identifiers turns into January. Excel is not corrupting the file at random; it
is applying a rule, and the rule runs earlier than most people expect. More
spreadsheet guides are in [Excel & Office](/topics/excel-office/). For problems elsewhere in a workbook, read
[why an Excel file becomes unusually large](/excel-file-size-too-large/).
Imports also deserve an outcome check: [an automation can succeed while losing useful data](/automations-failing-silently/).

## A cell's type is decided when you press Enter

A cell formatted as General has no type until something is entered in it. Excel
reads the characters, matches them against the patterns it knows, and picks one.
A string of digits becomes a number. Something that looks like a date becomes a
date. Anything left over stays text.

The patterns that read as dates are broader than people assume. Two numbers
separated by a hyphen or a slash qualify. So does a number followed by a month
abbreviation, which is how identifiers like MAR1 and SEP2 become dates. This
caused enough damage in published genetics research that the naming body
eventually renamed the affected genes rather than keep fighting the spreadsheet.

## Why the value is already gone

Excel stores dates as serial numbers counted from a fixed starting point, with
the display format applied on top. Once the conversion has happened, the cell
holds a number. Your original characters were never stored.

That is why the obvious repair does not work. Selecting the column and setting
the format to Text tells Excel how to display what is in the cell, and what is
in the cell is now a serial number. The display changes from a date to five
digits. It does not change back to the text you typed, because that text no
longer exists anywhere in the file.

<Callout type="warning" title="Undo is your only cheap repair">
  Immediately after a bad paste, undo still holds the previous state. Once the file has been
  saved and reopened, the original characters are gone and the column has to be re-imported
  from the source.
</Callout>

## Which conversions can be controlled

Microsoft documents Automatic Data Conversion options in current Excel, including
one for continuous letters and numbers that look like dates. JAN1 is its example.
Expressions containing spaces or punctuation may still be interpreted as dates.
The old version of this article said there was no conversion setting; that was
too broad. [Microsoft describes the available options and their limits](https://support.microsoft.com/en-us/excel/data-import-and-analysis-options-in-excel).

A setting that preserves a product code is not evidence that every import path
will preserve it. The input and Excel version still matter.

## Preserve text before conversion

Format the column as Text before any data goes into it. The format is read when
the entry is made, so setting it first means detection never runs. Pasting can also carry source formatting, so the import method and the
resulting cell value need checking.

Type a leading apostrophe for one-off entries. It instructs Excel to store the
characters as text and is not kept as part of the value.

Mark the column as text during import. Bringing data in through the import tools
rather than pasting gives you a per-column type choice, and that choice is
applied before any cell is written.

## What to do with a column that is already damaged

Re-import it from the source. Any attempt to convert the serial numbers back
assumes you can reconstruct the original string from the date, and for
identifiers that assumption usually fails on the ones that mattered.

A workbook that has been repaired this way several times tends to carry the
scars as bloat. If yours opens slowly, see
[why your Excel file is so large](/excel-file-size-too-large/).

If the source is gone, the serial numbers do at least tell you what was there.
A code that became 2 January came from something matching a day and month
pattern, and the surviving rows will show you which.
