A product code can become a date when Excel interprets the characters as a date
pattern. The result depends on regional settings and how the value enters the
workbook. More explanations are in [Excel & Office](/topics/excel-office/).

<Callout type="note" title="Correction, 27 October 2026">
  The earlier page treated date interpretation as identical across locales and import
  methods, and claimed Undo or re-import were the only recovery options. Those claims were
  too broad. This page explains conversion; it does not claim a tested repair procedure.
</Callout>

## Entry and display are different decisions

A date-like entry in a General-formatted cell can be interpreted as a date.
An example such as `1-2` is ambiguous: its meaning depends on regional date
conventions. It should not be described as always producing 2 January.

[Microsoft's date-conversion guidance](https://support.microsoft.com/en-us/excel/stop-automatically-changing-numbers-to-dates)
explains why text-like codes can be affected and describes text entry conventions.
The important distinction is between preserving the original characters at
entry and changing the appearance of a value already stored.

## A date value does not preserve every original character

Excel represents dates using serial values and applies a display format.
Microsoft documents its [1900 and 1904 date systems](https://support.microsoft.com/en-gb/excel/date-systems-in-excel),
including differences that matter when workbooks use different systems.

Once a code has become a date, a format change cannot reliably tell you whether
the source used a slash, a hyphen or a month name. Several source strings can
lead to a date value. Showing a serial number in place of a date therefore does
not establish that the identifier was recovered.

A surviving source export, an undo history or a previous workbook version may
provide evidence of the original. Their availability depends on the workflow.
The page should not promise that saved files always contain a recoverable
original, or that reopening always destroys every possible recovery route.

## Conversion controls have specific limits

Microsoft's [Automatic Data Conversion options](https://support.microsoft.com/en-us/excel/data-import-and-analysis-options-in-excel)
include a control for continuous letters and numbers such as `JAN1`. Its guidance
distinguishes that pattern from expressions containing spaces or separators,
which may still be recognised as dates.

A setting that handles one pattern is therefore not proof that every date-like
code will survive every import. The available controls and their behaviour
need to be checked for the Excel version and input path in use.

## Preserving identifiers means preserving text

Text entry, text-formatted destinations and explicit import types are related
ways of expressing that a code is a string. Microsoft's entry guidance describes
the leading apostrophe convention. These choices affect conversion before or
during entry; they cannot infer characters already lost.

Pasting can also bring formatting from the source. An import tool can infer a
type independently of the destination's appearance. The useful check is whether
the resulting identifier matches the source, including punctuation and leading
zeros, rather than whether the column merely looks plausible.

An [automation can report success while producing incorrect data](/automations-failing-silently/).
A finished spreadsheet import needs the same outcome check. File size is another
question: [a large workbook](/excel-file-size-too-large/) may contain excess
formatting, pictures or caches even when its identifiers are correct.
