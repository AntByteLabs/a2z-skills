A workflow can report successful executions while its destination remains
empty. The missing result is a different observation from an execution error. More automation guides are in
[Automation](/topics/automation/). A separately tested setup is in
[self-host n8n on Coolify](/self-host-n8n-coolify/), and another tool that is
confidently wrong is covered in
[why AI detectors flag human writing](/ai-detectors-flagging-human-writing/).

<Callout type="note" title="Correction, 27 October 2026">
  The earlier summary implied that expired credentials and rate limits always appear as
  successful runs. They can fail a run. The response handling and node configuration
  determine whether a failure remains visible.
</Callout>

## Execution status needs context

An execution status describes what the platform recorded. Unless the workflow
also checks its intended outcome, that status may not establish whether a record
arrived or a report contained the expected data. Platforms can support outcome
checks, but those checks need to be part of the workflow or monitoring.

That distinction is where silent failure lives. If every node runs and none of
them throws, the run is green. Whether the result is useful still depends on the checks configured for it.

## Empty is not an error

One possible cause is an empty result. A search step that matches nothing, a query
that returns no rows, a filter that excludes everything: each returns an empty
list, and an empty list is a valid result. The steps after it loop over nothing
and succeed at doing nothing.

This is also the failure that follows a small upstream change. A renamed field,
a changed label or a moved folder turns a working filter into one that matches
nothing, and the workflow carries on reporting success at its usual interval.

<Callout type="tip" title="Assert on the count">
  An expected record count can make a missing outcome visible. For a hypothetical report
  that should contain forty records, zero needs investigation. A normally empty report needs
  a different rule.
</Callout>

## Error handling that swallows

Retries and catch blocks can allow execution to continue after a problem,
depending on their configuration. A retry configured to give up and continue can produce
a run that looks fine and is missing data. A catch block that logs and
moves on has done the same thing more deliberately.

Whether retrying is appropriate depends on the cause and the operation. A
timeout does not establish that the remote action failed, so a retry may repeat
work. Error handling needs to preserve enough evidence to investigate the
outcome; n8n documents configurable [error workflows](https://docs.n8n.io/flow-logic/error-handling/).

## Partial data read as complete

An API can paginate using pages, cursors or another continuation mechanism. A workflow
that ignores the continuation processes that first page every time and reports
success. It worked correctly while the dataset was small, and started losing
records on the day the dataset outgrew one page.

A rate-limited API can return an error status that fails a node. A response body
may also contain an application-level error, depending on the API. Whether either
case remains visible depends on the response handling and node configuration.

A trigger that stopped firing is the same shape of problem, and on n8n it is
sometimes an endpoint registration problem: see
[n8n webhook not triggering](/n8n-webhook-not-working/).

## Credentials that expire into a valid response

An expired token can fail a request with an authentication error. If a workflow
continues after that error or substitutes an empty result, the execution outcome
can conceal missing work. It is too broad to say expired credentials always
appear successful: the API contract and error-handling settings matter.

## What to monitor instead

Include the intended outcome in monitoring. Useful checks include an alert
when a scheduled workflow has not run at all, alert when the record count falls
outside its normal range, and check the destination rather than the source, so
you are confirming that the rows arrived rather than that the query ran.

## Applying the distinction to n8n

A successful execution and a successful business outcome are different things
to measure. The expected result might be a saved record or a delivered message,
not merely the absence of an execution error. An empty result can also be
legitimate, so the workflow's purpose determines whether it needs attention.

The [official execution-history documentation](https://docs.n8n.io/workflows/executions/all-executions/)
describes filtering runs by workflow, status and execution time. These records
help establish which executions ran. Whether the intended record arrived or
message was delivered still needs evidence from the destination. A published
monitoring walkthrough would need a named tester's record of both sides.

## Related data and delivery problems

A successful expression can select the wrong person if a workflow replaces a matching-item reference with the first record. [n8n item linking](/n8n-item-linking-explained/) explains that distinction. [Webhook retries and duplicate events](/webhook-retries-duplicate-events/) covers a separate outcome problem: the same incoming notification causing work to happen again.

A spreadsheet import needs a similar check: [Excel can turn identifiers into dates](/excel-changing-numbers-into-dates/) even when the import finishes. A generated answer also needs evidence: [ChatGPT responses can vary](/chatgpt-different-answers-same-question/) without the wording alone establishing which answer is correct.
